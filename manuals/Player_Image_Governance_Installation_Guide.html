01
Decision gate

Assign people and record approvals

Before touching production, name the lead developer, deployment operator, database backup owner and LOC officer. Steven reviews the code and the exact diff. The LOC separately decides whether athlete portraits may be published and how consent evidence is checked. The release may be installed with the switch off before the LOC activation decision, but nobody should approve or enable images until that decision is recorded.

  • PR #5 is merged after code review; record its final full commit SHA.
  • Maintenance window and rollback owner are agreed.
  • LOC decision reference and consent review method are documented before publication.
  • A named LOC officer account exists; do not create a shared login or re-bootstrap an existing account.
Separate consentThe existing accreditation consent record does not establish consent to display a photo on the website. The LOC screen records only a reference to the specific publication-consent evidence, not the evidence document or private identity details.

03
Immutable source

Pin the final reviewed commit

Fetch into the retained checkout without changing the live release. Enter the full merge commit SHA from the approved PR, not merely the draft-branch head. The approved commit must be on origin/main; a squash merge need not preserve the draft branch's commit SHA.

Bash · review gate
cd "$GIT_ROOT"
git fetch origin
read -r -p "Full approved merge commit SHA: " APPROVED_COMMIT
[[ "$APPROVED_COMMIT" =~ ^[0-9a-f]{40}$ ]] || { echo "STOP: invalid SHA"; exit 1; }
export APPROVED_COMMIT
git cat-file -e "$APPROVED_COMMIT^{commit}"
git merge-base --is-ancestor "$APPROVED_COMMIT" origin/main
git diff --name-status "$EXPECTED_BASE" "$APPROVED_COMMIT"
git show "$APPROVED_COMMIT:apps/api/drizzle/0042_player_photo_publication.sql" | head -n 8

Review every changed path. This release should add migration 0042 and its journal entry, API publication controls, the LOC platform screen, website and lineup URL handling, and documentation. An unexpected migration, storage ACL, identity-document path, or unrelated application change needs a revised release plan. If production is no longer at the supplied dbd1783 baseline, compare the actual live commits before proceeding.

05
Recovery gate

Back up and rehearse in staging

First restore a fresh production backup to isolated staging with staging-only API domains and object-storage credentials. Apply 0042 there. Verify default-off output, privileges, one consented test approval, credential revocation, photo replacement and the emergency switch. Keep outbound mail, external webhooks and edge sync disabled in staging. Do not use real player portraits for a public staging site.

Before production migration, put the site into its established maintenance mode and pause all writers, scheduled jobs and edge sync. Back up the current database and the exact service configurations. Keep the active exported releases intact.

Bash · protected backup
export RELEASE_TIME="$(date -u +%Y%m%dT%H%M%SZ)"
export EVIDENCE_ROOT="/var/backups/gameday/player-images-$RELEASE_TIME"
install -d -m 0700 "$EVIDENCE_ROOT"
pg_dump "$MIGRATION_DATABASE_URL" -Fc -f "$EVIDENCE_ROOT/database-before.dump"
pg_restore --list "$EVIDENCE_ROOT/database-before.dump" > "$EVIDENCE_ROOT/database-restore-list.txt"
printf '%s\n' "$ACTIVE_API_RELEASE" > "$EVIDENCE_ROOT/previous-api-release.txt"
git -C "$GIT_ROOT" rev-parse HEAD > "$EVIDENCE_ROOT/source-commit-before.txt"

Store the verified website and platform release paths, Supervisor config file paths and copies, and the existing private storage snapshots under restricted access. A pg_restore --list check proves the archive is readable; the staging restore proves it can actually be recovered. Keep credentials and backup contents out of the deployment summary.

08
Build as the ISPConfig site user

Install dependencies and build three affected services

Use the release's pinned Node 24.14.0 and pnpm 9.15.0. Resolve absolute runtime paths from the host and ensure Supervisor will use the same runtime. The API, public website and platform must all be built from the same approved release. Teams and stats code do not change in this PR.

12
LOC officer · after decision

Review and approve exact images

  1. Sign in to https://platform.netballamericas.org/ with the named LOC account. Open Player images.
  2. Confirm the release is still Disabled. Select an accredited team. Only accredited teams appear in this list.
  3. For each player, choose Review current photo. Confirm it is the correct portrait; do not approve an identity document, an unclear photo or an unexpected image.
  4. Review separate evidence authorizing website publication. If the player was under 18 on the tournament eligibility date, verify guardian consent. For an adult, verify the player's consent.
  5. Enter only the evidence reference, not the form, identity number, phone number or a quote from the consent document. Choose Approve this exact photo.
  6. Repeat only for eligible players whose consent is confirmed. An uploaded photo alone is not approval; no bulk approval is part of this release.

The screen requires a current uploaded JPEG, current individual accreditation review, issued player credential, approved delegation and correct consent party. Approval is tied to the photo ID. Replacing the photo removes the prior approval; a new review and approval are required.

Do not force a blocked approval.If a person is marked ineligible, correct the underlying accreditation or photo workflow through the existing Teams and LOC screens. Do not patch player-photo metadata, issue a credential only to make a portrait appear, or update the public view by hand.
13
LOC release decision

Enable, verify, and monitor publication

After individual approvals and the recorded LOC decision, enter the decision reference under Website release in Player images, then choose Enable approved photos. Verify one explicitly approved player first. Keep the approved player's UUID inside restricted operational evidence.

Bash · substitute an LOC-approved player ID
read -r -p "Approved player UUID for verification: " APPROVED_PLAYER_ID
curl -sS -D - -o /dev/null "https://api.netballamericas.org/public/players/$APPROVED_PLAYER_ID/photo"
psql "$MIGRATION_DATABASE_URL" -X -v ON_ERROR_STOP=1 -c "SELECT player_photos_public_enabled FROM tournament"
psql "$MIGRATION_DATABASE_URL" -X -v ON_ERROR_STOP=1 -c "SELECT count(*) AS published_real_photos FROM v_public_player_photo"

The selected endpoint should return 200, Content-Type: image/jpeg, X-Content-Type-Options: nosniff, and Cache-Control: no-store. The public squad should contain public/players/{id}/photo for that approved player only. Check an unapproved player still returns 404. Do not print image bytes to the terminal or attach athlete portraits to a deployment ticket.

On staging, also exercise: wrong consent party, revoked credential, returned accreditation review, replacement photo, individual revoke, and global disable. In production, conduct those mutating tests only with a documented, authorized test profile or when a genuine revocation occurs. The squad JSON can briefly retain a cached path for up to its short refresh interval; the image endpoint must deny the bytes immediately after revoke or disable.

Recovery plan

Stop publication first; then roll back code if needed

  1. Fast kill switch: a named LOC officer opens Player images, records the decision/incident reference and chooses Disable all real photos. Verify v_public_player_photo returns zero rows and image requests return 404.
  2. If the LOC screen is unavailable: the authorized database operator may use the emergency SQL block below after checking there is exactly one tournament. Record the emergency change outside the app audit trail because direct SQL does not create a LOC audit event.
  3. If application cutover fails: restore the saved API, website and platform Supervisor stanzas to their recorded prior release directories, reread, and update only those programs. Verify each process path and health endpoint.
  4. Leave migration 0042 in place. It is additive. Do not drop the approval table or rewrite the Drizzle journal as a routine rollback. With the switch off, real photos remain hidden even if the old application is restored.
Bash · emergency database kill switch only
test "$(psql "$MIGRATION_DATABASE_URL" -X -Atc 'SELECT count(*) FROM tournament')" = "1" || { echo "STOP: unexpected tournament count"; exit 1; }
psql "$MIGRATION_DATABASE_URL" -X -v ON_ERROR_STOP=1 -c 'UPDATE tournament SET player_photos_public_enabled = false'
psql "$MIGRATION_DATABASE_URL" -X -Atc 'SELECT count(*) FROM v_public_player_photo'
Database restore is not the routine rollback.A full restore could discard registrations, accreditation reviews, consent decisions and match data created after the backup. Use it only through a separately reviewed recovery plan. Never make the bucket public to work around an image failure.
