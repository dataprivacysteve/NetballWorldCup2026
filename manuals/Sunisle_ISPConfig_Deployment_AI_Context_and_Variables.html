Section 1

How to use this profile

Fixed

Infrastructure rules

These are the defaults for every project: Debian 13, ISPConfig, Apache, GitHub, site-owned files, managed TLS, Supervisor for persistent Node processes and no Docker.

Per project

Deployment variables

The AI must collect repository, domain, ISPConfig IDs, site user, runtime, ports, database, storage, email, backup and release values.

Required output

Generated runbook

The AI must produce commands with placeholders, preflight gates, deploy-key setup, managed Apache configuration, acceptance tests and rollback.

Never include

Live secrets

This profile and generated templates must never contain real passwords, tokens, private keys, session secrets or personal production data.

Instruction to the receiving AITreat fixed values as infrastructure policy. Do not silently replace them with Docker, Nginx, Caddy, cloud-only hosting or a different control panel. If a project genuinely requires an exception, label it clearly and obtain approval.

Section 5

Required ISPConfig file layout

/var/www/clients/<ISPCONFIG_CLIENT_ID>/<ISPCONFIG_WEB_ID>/
├── web/
│   └── <PROJECT_SLUG>/
│       └── source/                 # Git checkout; application runs here
├── private/
│   └── <PROJECT_SLUG>-shared/
│       └── .env                    # real secrets; mode 0600
└── home/
    └── .ssh/
        ├── <PROJECT_SLUG>_prod     # private deploy key; never shared
        └── <PROJECT_SLUG>_prod.pub # public key; add to GitHub
export SITE_ROOT=/var/www/clients/<CLIENT_ID>/<WEB_ID>
export APP_ROOT="$SITE_ROOT/web/<PROJECT_SLUG>"
export SHARED_ROOT="$SITE_ROOT/private/<PROJECT_SLUG>-shared"
export SSH_DIR="$SITE_ROOT/home/.ssh"
Public-tree controlAlthough the application checkout must live in the ISPConfig web tree, Apache must proxy public traffic to the intended runtime or expose only a framework’s approved public build directory. Add managed Apache denial rules so repository source, .git, environment links, logs and internal files can never be downloaded directly.

Section 6

Standard GitHub deploy-key workflow

  1. Generate the key on the production server

    install -d -o "$SITE_USER" -g "$SITE_GROUP" -m 0700 "$SSH_DIR"
sudo -u "$SITE_USER" -H ssh-keygen -t ed25519   -C "<PROJECT_SLUG>-production-deploy"   -f "$SSH_DIR/<PROJECT_SLUG>_prod" -N ""
chmod 600 "$SSH_DIR/<PROJECT_SLUG>_prod"
chmod 644 "$SSH_DIR/<PROJECT_SLUG>_prod.pub"

  2. Print only the public key for handoff

    cat "$SSH_DIR/<PROJECT_SLUG>_prod.pub"

    The output begins with ssh-ed25519. The private file without .pub never leaves the server.

  3. Add it to the one repository

    GitHub → repository → Settings → Deploy keys → Add deploy key. Use a descriptive production-server title, paste the full public line and leave Allow write access unchecked.

  4. Verify access before cloning

    sudo -u "$SITE_USER" -H env   GIT_SSH_COMMAND="ssh -i $SSH_DIR/<PROJECT_SLUG>_prod -o IdentitiesOnly=yes"   git ls-remote git@github.com:<GITHUB_OWNER>/<GITHUB_REPOSITORY>.git refs/heads/main

    Validate GitHub’s published SSH host fingerprint before accepting a first-time host prompt.

Key policyOne repository-specific read-only key per production project. Do not reuse a developer’s personal key, copy a private key into chat/email, or enable write access for a pull-only deployment.

Section 7

Runtime and process rules

Node applications

Default to Node.js 22 LTS. Use the lockfile and pinned package manager. Bind production servers to 127.0.0.1; Apache provides public access.

PHP applications

Select the approved PHP-FPM version in ISPConfig. Serve only the framework’s public directory. Use Supervisor for persistent workers and ISPConfig cron for schedules.

Python applications

Use a project-owned virtual environment inside the application tree, a production WSGI/ASGI server on loopback and Supervisor for persistence.

All runtimes

Processes run as the ISPConfig site user, never root. Logs have project-specific paths. Configure clean stop, automatic restart and startup recovery.

Supervisor template

[program:<PROJECT_SLUG>-<SERVICE>]
directory=/var/www/clients/<CLIENT_ID>/<WEB_ID>/web/<PROJECT_SLUG>/source
command=<ABSOLUTE_START_COMMAND>
user=<SITE_USER>
environment=<NON_SECRET_RUNTIME_FLAGS>
autostart=true
autorestart=true
startsecs=8
stopasgroup=true
killasgroup=true
stdout_logfile=/var/log/<PROJECT_SLUG>/<SERVICE>.log
stderr_logfile=/var/log/<PROJECT_SLUG>/<SERVICE>-error.log

Section 8

ISPConfig and Apache requirements

  • Create DNS before requesting Let’s Encrypt.
  • Create exact hostnames under ISPConfig Sites → Website.
  • Enable SSL, Let’s Encrypt and HTTP-to-HTTPS redirection.
  • Disable directory listing, CGI, SSI and WebDAV unless explicitly required.
  • Apply custom rules through ISPConfig directives/templates only.
  • Do not expose application ports publicly.
  • Preserve the original host and forward HTTPS scheme information.
  • Test apachectl configtest before reload.

Reverse-proxy pattern

ProxyPreserveHost On
RequestHeader set X-Forwarded-Proto "https"
ProxyPass        / http://127.0.0.1:<APP_PORT>/ retry=0 timeout=120
ProxyPassReverse / http://127.0.0.1:<APP_PORT>/

Source protection pattern

<Directory "/var/www/clients/<CLIENT_ID>/<WEB_ID>/web/<PROJECT_SLUG>">
  Require all denied
</Directory>
Framework-specific adjustmentThe generated template must reconcile the denial rule with the application’s serving model. A pure Apache/PHP app may instead set its document root to the approved public subdirectory. A proxied Node/Python app can deny direct filesystem serving and proxy all requests.

Section 10

Required release lifecycle

PreflightBackupFetch tagsCheckout approved tagLocked installBuildMigrate onceRestartSmoke testRecord evidence

  1. Preflight

    Confirm clean working tree, disk/RAM, runtime versions, DNS, TLS readiness, data connectivity, secret completeness and rollback tag.

  2. Deploy exact release

    Use an annotated approved tag. Record tag and commit SHA. Do not deploy a moving branch or develop on production.

  3. Migrate safely

    Back up first, run the release migration command once and prohibit destructive demo/seed commands in production.

  4. Verify end-to-end

    Test health endpoints, authentication, authorization, primary business workflow, uploads/email where applicable, restart recovery and absence of deferred services.

  5. Rollback

    Document application rollback separately from data restoration. Never reverse destructive schema changes casually; validate backups outside production first.

Section 11

What the deployment-template AI must produce

  • Rich-text HTML runbook suitable for browser viewing and printing.
  • A values table separating confirmed values from unresolved placeholders.
  • Stop/go gates for missing domains, access, secrets, storage, email, backup and dates.
  • Exact GitHub public deploy-key generation, handoff and verification commands.
  • ISPConfig website creation, DNS, TLS and managed Apache instructions.
  • Correct web-tree application path and protected private-tree secrets path.
  • Runtime package, locked dependency, build and start commands.
  • Supervisor definitions for each persistent service.
  • Database/cache/object-storage provisioning with private network boundaries.
  • Pre-deployment backup and isolated restore proof.
  • Health, security and full business-workflow acceptance matrix.
  • Update procedure, clean-tree rule and rollback procedure.
  • Final launch checklist and evidence-return list.
  • No real credentials, private keys or invented infrastructure values.
