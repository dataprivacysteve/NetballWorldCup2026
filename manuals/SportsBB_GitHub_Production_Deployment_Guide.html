Chapter 1

Exactly what goes live

Production receives one fixed Phase 1 tag. GameDay development continues safely on another branch and isolated UAT data; it does not run on the live server.

Live

API

Authentication, registration, roster, officials, private document upload, review state and accreditation.

Live

Team Portal

One authorised team officer manages each delegation through teams.netballamericas.org.

Live

LOC Platform

The one named LOC officer manually verifies and approves through platform.netballamericas.org.

Dormant

Phase 2

No public website, scoring, clock, edge sync, statistics or broadcast process starts.

Database safetyEmpty Phase 2 tables may exist because the monorepo shares migration history. Tables alone do not activate features or corrupt registration.
Hard separationNever point local demos, tests or the Phase 2 branch at production PostgreSQL, Redis or object storage. Phase 2 UAT needs separate data, Redis namespace and buckets.

Chapter 5

Create three ISPConfig websites

  1. Create DNS

    Create only Phase 1 A records—api, teams, platform—to 67.212.87.195. Use TTL 300 during setup.

  2. Create websites

    In ISPConfig → Sites → Website, add each exact hostname with Apache. Enable SSL and Let’s Encrypt after DNS resolves and force HTTPS. Disable directory listing, CGI, SSI and WebDAV.

  3. Protect source

    Place the repository under the API site’s private directory, owned by the ISPConfig site owner/group. Nothing in the repository belongs under a public web directory.

  4. Restrict until accepted

    Use VPN, IP allow-list or ISPConfig password protection until the complete registration-to-approval test passes.

ISPConfig ownershipNever edit generated vhost files. Add proxy rules through ISPConfig’s managed Apache directives or site-template mechanism.

Chapter 7

Provision data services

  1. PostgreSQL

    Prefer ISPConfig’s database facility when PostgreSQL is configured; otherwise the DBA creates gameday and least-privilege roles for runtime API, LOC platform, shared public access and migrations. The API requires all four URLs even while the public website is deferred.

    sudo -u postgres psql
CREATE ROLE gameday_app LOGIN PASSWORD '<STRONG_PASSWORD>';
CREATE ROLE gameday_platform LOGIN PASSWORD '<STRONG_PASSWORD>';
CREATE ROLE gameday_public LOGIN PASSWORD '<STRONG_PASSWORD>';
CREATE ROLE gameday_migrator LOGIN PASSWORD '<STRONG_PASSWORD>';
CREATE DATABASE gameday OWNER gameday_migrator ENCODING 'UTF8';
REVOKE ALL ON DATABASE gameday FROM PUBLIC;
\q

    Grant only required schema/table rights after migration. No runtime connection uses the PostgreSQL superuser.

  2. Redis

    Bind Redis to loopback/private interfaces, retain protected mode and configure authentication/ACLs. Never expose 6379.

    redis-cli -h 127.0.0.1 PING
ss -lntp | grep 6379

  3. Private object storage

    Provision an approved S3-compatible service and separate production buckets for photos, badges and identity evidence. Identity documents are never public. This is an existing/managed service, not a Docker container.

Chapter 8

Install the approved GitHub tag

  1. Create private release root

    export SITE_USER=<ISPCONFIG_SITE_USER>
export SITE_GROUP=<ISPCONFIG_SITE_GROUP>
export APP_ROOT=/var/www/clients/<CLIENT>/<API_WEB>/private/gameday
install -d -o "$SITE_USER" -g "$SITE_GROUP" -m 0750 "$APP_ROOT"

  2. Create a read-only deploy key

    Run ssh-keygen -t ed25519 as the site user, store the private key in that user’s protected ~/.ssh, and add only the public key to GitHub without write access.

  3. Clone and detach at the tag

    sudo -u "$SITE_USER" -H env GIT_SSH_COMMAND='ssh -i ~/.ssh/gameday_prod -o IdentitiesOnly=yes' git clone git@github.com:<GITHUB_ORG>/sportsbb-gameday.git "$APP_ROOT/source"
cd "$APP_ROOT/source"
sudo -u "$SITE_USER" -H git checkout --detach v2026.07.31-registration
git rev-parse HEAD

    Record the exact SHA.

  4. Create protected shared configuration

    install -d -o "$SITE_USER" -g "$SITE_GROUP" -m 0750 "$APP_ROOT/shared"
install -o "$SITE_USER" -g "$SITE_GROUP" -m 0600 /dev/null "$APP_ROOT/shared/.env"
ln -s "$APP_ROOT/shared/.env" "$APP_ROOT/source/.env"

Chapter 10

Install, build and migrate

  1. Locked dependencies

    cd "$APP_ROOT/source"
sudo -u "$SITE_USER" -H pnpm install --frozen-lockfile

  2. Build Phase 1 only

    sudo -u "$SITE_USER" -H pnpm --filter api build
sudo -u "$SITE_USER" -H pnpm --filter teams build
sudo -u "$SITE_USER" -H pnpm --filter platform build

  3. Back up, then migrate once

    pg_dump -h 127.0.0.1 -U gameday_migrator -Fc gameday -f /secure/backup/gameday-predeploy.dump
sudo -u "$SITE_USER" -H pnpm --filter api db:migrate

    Migrations through 0027 may create dormant Phase 2 structures; they do not activate GameDay.

  4. Bootstrap SportsBB control

    sudo -u "$SITE_USER" -H pnpm --filter api db:bootstrap-control

    After verified login, remove the one-time password from runtime configuration.

ProhibitedNever run pnpm --filter api db:seed in production; it truncates tables and creates demo users.

Chapter 14

Prove backup and recovery

  1. Capture all state

    Acroknight/Sunisle backs up PostgreSQL, private object buckets and the protected environment daily, encrypted, with one-year retention.

  2. Deployment checkpoint

    pg_dump -h 127.0.0.1 -U gameday_migrator -Fc gameday -f /secure/backup/gameday-$(date +%F-%H%M).dump
sha256sum /secure/backup/gameday-*.dump

  3. Restore in isolation

    Restore database and objects outside production and verify a known synthetic record and document.

  4. Record proof

    Record backup ID, checksum, times, destination, verifier and result. A job is not accepted until a restore succeeds.

Chapter 15

Deploy future tags

  1. Checkpoint

    cd "$APP_ROOT/source"
git status --short
git describe --tags --always
git rev-parse HEAD

    If status prints anything, stop and review; do not reset, stash or overwrite server changes.

  2. Fetch approved tag

    git fetch --tags --prune
git checkout --detach <APPROVED_TAG>
git rev-parse HEAD

  3. Build, migrate, restart

    pnpm install --frozen-lockfile
pnpm --filter api build
pnpm --filter teams build
pnpm --filter platform build
pnpm --filter api db:migrate
supervisorctl restart gameday-api gameday-teams gameday-platform

  4. Repeat acceptance

    Record tag, SHA, operator, migration, tests and prior rollback tag.

Chapter 16

Rollback safely

  1. Assess schema compatibility

    Do not improvise reversal of a destructive migration. Confirm previous code can read the current schema.

  2. Application rollback

    supervisorctl stop gameday-api gameday-teams gameday-platform
cd "$APP_ROOT/source"
git checkout --detach <PREVIOUS_SUCCESSFUL_TAG>
pnpm install --frozen-lockfile
pnpm --filter api build
pnpm --filter teams build
pnpm --filter platform build
supervisorctl start gameday-api gameday-teams gameday-platform

  3. Data restoration, if required

    Keep production stopped. Validate the pre-deploy database and object backups in isolation, then follow the approved restore procedure.

  4. Verify and record

    Repeat the Phase 1 acceptance matrix and document impact, failed tag, restored tag and owner.

  • LOC email, email domain and launch/install dates corrected.

  • No Docker, Compose, Caddy or Node systemd units.
  • Ports 3000, 3002 and 3003 listen on loopback only.
  • PostgreSQL, Redis and identity storage are private.
  • Migrations passed and production seed was never run.
  • Only API, Team Portal and LOC Platform processes run.
  • One SportsBB administrator and one LOC officer authenticate.
  • Registration → roster → upload → LOC approval → accreditation test passed.
  • Authorization and password-reset tests passed.
  • Encrypted daily off-server backup and isolated restore passed.
  • Controlled restart recovery passed.
  • Release SHA, ISPConfig IDs, backup ID and acceptance owners recorded.
